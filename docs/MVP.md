# OrderRoom MVP仕様

更新日: 2026-07-22

この資料は、[ロードマップ](ロードマップ.md)で定めたコア版と統合MVPの機能範囲、権限、完成シナリオを管理する。期限、実装順、縮退判断はロードマップを優先する。

## 概要

OrderRoomは、大学生のBBQ、宅飲み、旅行、学園祭などで、参加者と幹事が欲しい物を提案し、幹事が採用・見送り・再検討を決め、買い物、実購入額、均等割り、立替精算まで共有するログイン不要のWebアプリである。

相談や合意形成は外部チャット、提案から精算記録まではOrderRoom、実際の送金は外部の決済サービスで行う。

## MVPを二段階に分ける

### コア版: 2026-07-31

購入前の意思決定と買い物を完遂する。

> 作成 → 共有 → 幹事参加 → 提案 → 編集・削除 → 採用・見送り・提案中へ戻す → 購入済み変更 → 見積集計

### 統合MVP: 2026-08-07

コア版に購入後の精算記録を加える。

> 実購入額・購入者 → 精算対象者 → 均等割り → 立替精算案 → 精算済み記録

## 確定仕様

### 利用対象

大学生のイベント幹事・参加者。

### 参加方法

共有URLを開き、表示名だけ入力する。

### 参加URL

`/rooms/{roomId}` を使う。`roomId` はUUID。

### ホストURL

`/rooms/{roomId}/host?key={hostKey}` を使う。

### ルーム作成項目

`title / eventDate / memo / budgetAmount` を登録する。

### 予算上限

`budgetAmount` は任意、0円以上。未入力なら予算差分を表示しない。

### 幹事の提案参加

幹事も参加者として表示名を登録し、`participant token` を持つことで商品を提案できる。

### 商品項目

`name / price / quantity / memo` を登録する。

### 見積単価

`price` は見積単価として扱い、UIでも「見積単価」と表示する。

### 商品状態

- API状態: `proposed / accepted / rejected`
- UI状態: 提案中／採用／見送り
- 見送りデータは削除せず保持し、通常画面では非表示にする。

### 集計

- メイン合計: acceptedの `price × quantity` の合計。
- 補助合計: proposedの `price × quantity` の合計。
- 予算差分: `budgetAmount - acceptedTotalPrice`。

### 購入チェック

acceptedだけ購入済みに変更できる。

### 実購入額と購入者

- 実購入額: acceptedかつ購入済みの商品へ、その商品行の実際の支払総額を記録する。
- 購入者: 購入済み商品ごとに一人を記録する。

### 精算

- 精算対象者: ホストが参加者から選ぶ。初期値は全参加者。
- 割り勘方式: 実購入額合計を精算対象者で均等に分ける。
- 端数: 1円単位。参加登録順の早い人から1円ずつ加算する。
- 立替精算: 各人の負担額と立替額から送金案を算出する。
- 精算記録: 送金案ごとに未精算／精算済みを記録する。

### 同期

リアルタイム同期は行わず、手動更新で再取得する。

### 決済

アプリ内決済は行わない。送金はアプリ外で行う。

## 権限

### ルーム閲覧

- 参加者: 可。
- ホスト: 可。

### 商品提案

- 参加者: 可。
- ホスト: 可。幹事自身も参加者として登録した後に提案できる。

### 自分の提案編集・削除

- 参加者: 可。
- ホスト: 可。

### 他人の提案編集・削除

- 参加者: 不可。
- ホスト: 可。

### 採用・見送り・提案中へ戻す

- 参加者: 不可。
- ホスト: 可。

### 購入済みチェック

- 参加者: 不可。
- ホスト: acceptedの商品だけ可。

### 実購入額・購入者の登録

- 参加者: 不可。
- ホスト: 可。

### 精算対象者の選択

- 参加者: 不可。
- ホスト: 可。

### 精算済み記録

- 参加者: 自分が支払側の精算だけ可。
- ホスト: 全件可。

### 精算のリセット

- 参加者: 不可。
- ホスト: 可。

### 幹事の2つの役割

幹事は、参加者としての役割と、管理者としての役割を同時に持てる。

#### 参加者としての幹事

幹事自身が「買いたいもの」を提案するための役割。

- できること
  - 幹事画面で表示名を登録する
  - 自分の提案を追加する
  - 自分の提案を編集する
  - 自分の提案を削除する
- 使う認証
  - `participant token`

#### 管理者としての幹事

ルーム全体を管理するための役割。

- できること
  - 提案を採用する
  - 提案を今回は見送る
  - 提案を提案中に戻す
  - 採用済み提案を購入済みにする
  - 購入済み提案を未購入に戻す
  - すべての提案を編集する
  - すべての提案を削除する
- 使う認証
  - `hostKey`

補足:

- 幹事が参加者として登録しても、管理者権限は失わない。
- 幹事が未参加の場合でもhostKeyによる管理操作はできる。
- 幹事が商品提案を行うには、参加者として表示名登録し、participant tokenを持つ必要がある。
- `participant token` と `hostKey` は別物として扱う。

### 提案編集・削除

- 編集対象は商品名、見積単価、数量、メモに限定する。
- 参加者は自分の提案だけ編集・削除できる。
- 幹事はすべての提案を編集・削除できる。
- 他の参加者は他人の提案を編集・削除できない。
- 削除前には確認を出す。
- 編集をキャンセルした場合は元の内容を保持し、保存するまで一覧や集計へ反映しない。

### 提案編集の再承認

- 参加者がacceptedの商品を編集した場合はproposedへ戻す。
- ホストが編集した場合はacceptedを維持できる。
- statusとpurchasedは通常の内容編集APIでは変更しない。

### 幹事による状態管理

- 幹事だけが各提案をaccepted、rejected、proposedへ変更できる。
- UI表示はaccepted=採用、rejected=今回は見送る、proposed=提案中に戻すとする。
- acceptedの商品だけpurchased=trueへ変更でき、未購入に戻すこともできる。
- status変更、purchased変更、編集、削除の後は、一覧、採用済み合計、提案中合計、予算との差額を即時更新する。

## tokenとhostKey

- 参加成功時に参加者tokenを一度だけ返す。
- FEはtokenをルーム単位で `localStorage` に保存する。
- 参加者操作では `X-Participant-Token` を送る。
- ホスト画面はURLのkeyを初回読込時に `sessionStorage` へ移す。
- 可能なら初回読込後にkeyをアドレスバーから除去する。
- ホスト操作では `X-Host-Key` を送る。
- tokenとhostKeyは一覧レスポンス、通常画面、ログへ出さない。
- 参加URLとホストURLを区別し、ホストURLには共有禁止の警告を出す。

## 精算の固定ルール

- 見積額ではなく実購入額だけを使用する。
- 実購入額または購入者が未入力の商品は計算対象外にし、警告を表示する。
- 精算対象者が0人の場合は計算しない。
- 各人の負担額合計は実購入額合計と一致させる。
- 各人の立替差額合計は0円にする。
- 同じ入力なら毎回同じ端数配分と送金案を返す。
- 精算済みが1件でもある場合、実購入額、購入者、精算対象者を変更できない。
- ホストが全精算をリセットした場合だけ、計算元を再編集できる。

## 保留中の仕様

- ホストによるルーム情報編集。
- ルーム終了状態の管理。
- ルームの物理削除。
- 商品メモ機能の扱い。room-pageでは商品名、見積単価、数量を一列に並べるとUIが崩れやすい懸念があり、FEではボトムシート形式でメモを確認・編集する案がマージ済み。ただしAPI接続は未実装のため、MVPで永続化まで含めるかはPMとFE/BEで判断する。
- 参加コード方式。参加URLのUUID直開きではなく、参加者が短い参加コードを入力する案がある。採用する場合も内部の`roomId`はUUIDのまま維持し、利用者向け識別子として`roomCode`を追加する。
- ホスト承認制。参加者が参加リクエストを送り、ホスト承認後に参加確定する案がある。これは「表示名だけで即時参加」というMVPの参加性と衝突するため、MVP後の検討候補とする。

これらは、データ保持、精算済みデータとの整合、権限、期限、参加性への影響をPMが決定するまでMVPへ追加しない。

## MVPに含めないもの

- QRコード
- ルーム一覧、参加履歴一覧
- ルームの物理削除、ルーム終了状態の管理
- チャット、投票、通知
- AI機能、レシートOCR
- アプリ内決済、送金代行
- 重み付き割り勘、割合指定、個別商品の負担者指定
- 運転手割引、飲酒有無による自動調整
- 商品マスタ、店舗メニュー連携、モバイルオーダー連携
- リアルタイム同期
- 参加コードによる入室
- ホスト承認制の参加フロー

## 完成シナリオ

MacとiPhoneなど2台以上で、次を本番環境上で順番に完遂できること。

1. ホストがイベント名、開催日、メモ、任意の予算上限でルームを作る
2. 参加URLをコピーして共有する
3. 幹事画面で幹事自身が参加者として表示名を登録する
4. 幹事が商品名、見積単価、数量、メモを提案する
5. 別の利用者が共有URLを直接開く
6. 表示名だけ入力して参加する
7. 参加者が商品名、見積単価、数量、メモを提案する
8. 提案者本人が自分の提案を編集・削除する
9. ホストが任意の提案を編集・削除する
10. ホストが提案を採用、今回は見送る、提案中に戻す
11. 採用品だけを買い物リストへ表示する
12. 採用品へ購入済みチェックを付け、未購入にも戻せる
13. 採用済み見積、提案中見積、予算差分、商品別数量を表示する
14. 購入済み商品へ実購入額と購入者を記録する
15. 精算対象者を選び、均等割りの負担額を表示する
16. 複数購入者の立替額から送金案を表示する
17. 支払側本人またはホストが精算済みを記録する
18. 手動更新で別端末の変更を取得する
19. 空状態、読込中、通信失敗、存在しないルームを表示する

## 完成判定

- コア版は購入前導線、幹事参加、提案追加、編集、削除、採用、見送り、提案中へ戻す、購入済み変更、集計更新が完遂でき、P0バグが0件なら完成。
- 統合MVPは購入後の精算導線まで完遂でき、P0バグが0件なら完成。
- モックUIやAPI単体実装は、利用者導線の完成とは扱わない。
- 詳細な画面受け入れ条件は[画面仕様](screens.md)を使う。
- APIと計算の受け入れ条件は[DB・API設計書](DB_API設計書.md)を使う。
- 幹事、提案者本人、第三者の3パターンで権限テストを追加する。
- 編集、削除、採用、見送り、提案中へ戻す、購入状態変更後に合計表示が正しく更新されることを確認する。
- `npm run lint`、`npm run build`、バックエンドテストがすべて成功することを確認する。
- ローカル起動で、幹事作成 → 幹事参加 → 提案追加 → 編集 → 採用 → 購入済み → 削除までを確認する。
